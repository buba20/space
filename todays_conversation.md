User: can you explain what this liveness probe does

    livenessProbe:
      exec:
        command:
          - sh
          - -c
          - test $(cat /proc/1/smaps | grep -i pss |  awk '{Total+=$2} END {print int(Total/1024)}') -le 2048

Assistant: This liveness probe executes a command inside the container
to check its memory usage (PSS - Proportional Set Size). It sums up the
memory used by the main process (PID 1 inside the container) and
compares it against a threshold (2048 MB). If the memory usage is less
than or equal to 2048 MB, the probe succeeds; otherwise, Kubernetes
considers the container unhealthy and restarts it.

------------------------------------------------------------------------

User: Can you explain

Assistant: In simpler terms:\
- Kubernetes runs this command every X seconds (based on the probe
configuration).\
- The command calculates how much memory the main process inside the
container uses (measured in MB).\
- If the value is `<= 2048` (2 GB), the container is considered
healthy.\
- If it is greater, Kubernetes kills and restarts the container.

So this probe protects against memory leaks --- if the process exceeds
the memory budget, the container gets restarted automatically.

------------------------------------------------------------------------

User: Wouldn't this solution have the same effect?

Assistant: Not exactly --- the effect would be similar but not
identical. In Kubernetes you usually control memory usage with resource
`requests` and `limits`.\
- If you set a **memory limit** (`resources.limits.memory`), the
kubelet/cgroup enforces it. If the process exceeds this limit, the
kernel's OOM killer terminates the container.\
- The liveness probe is different: it is an **application-level check**,
not enforced by the kernel. It allows you to restart the container
*before* it hits the hard limit, or with a more flexible condition.

So:\
- **Memory limit** = hard technical boundary, process dies when
exceeded.\
- **Liveness probe with memory check** = soft, configurable guardrail
you can adapt to your needs.

User: Where does `container_cpu_usage_seconds_total` come from?

Assistant: That metric is generated by **cAdvisor**, which runs inside
the kubelet on every node.\
- It collects CPU, memory, filesystem, and network usage per container
from Linux cgroups.\
- Prometheus scrapes kubelet's `/metrics/cadvisor` endpoint, where it
exposes `container_cpu_usage_seconds_total` (cumulative CPU time in
seconds).\
So:\
`container_cpu_usage_seconds_total` = sum of CPU seconds used by the
container's processes, as reported by cgroups → exposed by
kubelet/cAdvisor → scraped by Prometheus.

User: Unfortunately I work with very limited permissions and don't have

Assistant: Yes 🙂. If you can't use metrics-server or global cAdvisor
metrics, you still have a few options:

1.  **From inside the pod**

    -   CPU/memory usage is tracked by cgroups.\
    -   Example files:
        -   `/sys/fs/cgroup/cpuacct/cpuacct.usage` (nanoseconds of CPU
            time)\
        -   `/sys/fs/cgroup/cpu.stat` (v2: usage in microseconds)\
        -   `/sys/fs/cgroup/memory/memory.usage_in_bytes`\
        -   `/sys/fs/cgroup/memory.current` (v2)\
    -   You can read these and compute usage.

2.  **From Kubernetes Metrics API** (if `metrics-server` is installed
    and RBAC allows)

    ``` sh
    kubectl get --raw "/apis/metrics.k8s.io/v1beta1/namespaces/<ns>/pods"
    ```

    Returns CPU/memory usage per container in the namespace.

3.  **Custom OTEL metric**

    -   Since you already use OpenTelemetry, you can build a small
        helper that reads from `/sys/fs/cgroup/` and publishes metrics
        (`app_cpu_usage`, `app_memory_usage`).\
    -   Prometheus will scrape these alongside other metrics.

4.  **ServiceAccount & RBAC**

    -   You could grant your app's SA `get` on `pods.metrics.k8s.io` in
        its namespace.\
    -   Then the app could query Kubernetes API for its own metrics.

✅ Easiest: read `/sys/fs/cgroup` inside the pod → export via OTEL.
